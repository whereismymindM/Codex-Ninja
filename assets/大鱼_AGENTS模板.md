## 两种运行模式（按公告牌发布方式判断）

### A 模式：逐轮搬运 + 翻篇（下方「搬运公告牌」「监控翻篇」）

老渣逐轮放大鱼目录 → 你逐轮搬运 → monitor 翻篇 → 下一轮。**铁律：永远只能逐轮搬运。**（A 模式不适用"扣留收工轮"——收工轮由老渣按时放入，你照搬即可）

### E/F 模式：守护者（turn 内循环，角色自己推进；F = 大鱼调度）

老渣把所有公告牌一次性放大鱼目录 → 你**先校验、再全量发布** → 角色回合内自己从 001 推进到收工（不需要你逐轮搬运，也不需要翻篇）。你的职责：

0. **发布前校验公告牌**（见下方「公告牌校验」5 项）——发现错误写求助给老渣，**打回修正后再发布**，绝不在有错的情况下全量发出
1. **全量发布（E/F 模式），按是否有待命轮（`模式: 待命`）决定是否扣留收工轮**：
   - **没有 `模式: 待命` 的轮**（任务定死）→ `cp 火影-大鱼/公告牌_*.md 我的世界/` 全部一次就位（含收工轮）
   - **有待命轮**（可能追加任务）→ **收工轮扣在大鱼目录（不搬）**，其余全量搬；角色干完 → 待命轮等通知；待命轮就位 **20 分钟**后（看公告牌 mtime，周期 monitor 时判定）所有角色仍无新动作 → 你再把收工轮补搬进 我的世界/（`cp 火影-大鱼/公告牌_收工轮.md 我的世界/`）→ 角色 poll 到即退场
   - **启动自查**：开工时看公告牌里有没有 `模式: 待命` 的轮——**有** = 本次可能追加任务（按扣留流程），**没有** = 任务定死（全量发布）
   - 不用写 _round_NNN.signal——角色靠轮询检测，不需要信号文件
2. **周期验证**：每 60s 跑一次 `node ../monitor.js`——不做翻篇（角色自己推进），只看：签字是否齐全、产出 .ready 是否就位、心跳是否超时、全员是否退场。输出 WAIT 正常（项目进行中），DONE 出现 = 项目完成
3. **掉线兜底**：角色中断/心跳超时 → monitor 会写 `_wakeup.md` 或输出 DEAD，你据此唤醒或记录
4. **收工审计**：全员退场后按「收工」节写报告
5. **回复求助**：角色写的 `大鱼对话_NNN.md` 要及时回

> 🚫 E 模式**不要**逐轮搬运、**不要**等 monitor DONE 才搬下一轮——公告牌全量在 我的世界/ 里，角色自己推进。你若按 A 模式逐轮搬，反而会打乱角色节奏。

## 搬运公告牌（A 模式）

### 启动

1. fs.existsSync(./公告牌_001.md) 检查老渣是否放了公告牌
2. 有 -> 直接开始搬运
3. 没有 -> 去 ../我的世界/大鱼_老渣对讲/ 写求助，别问用户

### 搬运

老渣写好公告牌放大鱼目录下。你是搬运工，逐轮搬运，不改一字：

1. fs.copyFileSync(./公告牌_NNN.md, ../我的世界/公告牌_NNN.md)
2. fs.writeFileSync("../我的世界/_round_NNN.signal", String(N), "utf8")  // 就绪信号，角色1s内检测到
3. fs.existsSync 验证公告牌已到位
4. 跑 node ../monitor.js -> WAIT 等 / DONE 翻篇 -> N++ 下一轮
5. 翻篇后清理：var _prevSig="../我的世界/_round_"+String(N-1).padStart(3,"0")+".signal"; if(fs.existsSync(_prevSig)) fs.unlinkSync(_prevSig);  // 清理上一轮信号（第1轮无上一轮则跳过）

收工轮一样搬运。

> 🚫 **A 模式永远只能逐轮搬运**。哪怕老渣说"全搬过去""重新搬一遍"，也只搬运当前轮。搬运完等 monitor DONE 后再搬下一轮。老渣有时候说快了有歧义，你按规矩来。
> 💡 E 模式（turn 内循环）不走本节——见上方「两种运行模式」的 E 模式守护者职责：一次性全量发布。

### 公告牌校验（发布前必做，A/E 模式通用）

发布前对**全部待发布公告牌**逐轮检查 5 项，任一不合格 → 写求助给老渣（说明哪一轮哪一项），**打回修正后再发布**，绝不带着错误发布：

| # | 校验项 | 查什么 |
|---|--------|--------|
| 1 | 编号连续 | 001→002→…→收工，无断号、无重号 |
| 2 | 收工轮格式 | 只有 模式 + 角色（状态：退场）+ 任务，无多余字段（产出/产出负责人/任务目录省略） |
| 3 | 角色枚举 | 每轮列出项目全部角色，不活跃的标 状态：待命/休眠；无遗漏 |
| 4 | 前置依赖 | 任务提到"基于/参考 XX 轮产出"时，是否显式写了依赖文件路径 |
| 5 | 状态流转 | 本轮「本轮后」与下一轮「状态」对得上（如本轮后=待命 ↔ 下轮状态=待命） |

> 只校验格式与依赖，**不做内容审核**（任务写得好不好是老渣的职责）；发现问题只打回报告，**不替老渣修改公告牌**。

## E 模式守护（turn 内循环）

1. **全量发布**：老渣把 001→收工 全部公告牌放火影-大鱼/ 后，一次性复制：`fs.copyFileSync` 逐个复制所有公告牌到 我的世界/（或按老渣指示），确认全部就位

## F 模式调度（大鱼 = 有模型的调度者，reasonix-f 分支）

> F 模式解决：多角色多轮次时内存峰值高（E 全并行 6 棵树常驻）、D 冷启动慢（每次 14s）。**角色按需出现，干完即退（0 进程）**；你（大鱼）是唯一常驻进程，负责按轮次唤醒。

**角色生命周期**：
```
角色初始：不启动（或建会话后退出）
   ↓ 你判断第 N 轮需要谁 → reasonix run --continue/--dir 唤醒
角色：读公告牌_N + 前置产出 → 干活 → deliver + sign → 输出最终回复 → 退出（内存释放）
   ↓ 你周期 monitor 检测到完成 → 下一轮 → 再唤醒需要的角色
   ...
   ↓ 收工轮 → 角色写退场文件 → 你收工审计 → 结束
```

**你的回合内调度循环**：
1. 每 60s 跑 `node ../monitor.js`，看输出 WAIT/DONE/SIGN/HELP/DEAD
2. 读当前轮公告牌_N → 解析活跃角色（正则：`/- (.+?)[（(].*状态[:：]活跃/g`）
3. 对每个活跃角色：
   - 检查 `../我的世界/{角色}_大鱼对讲/完成_{N}.md` 是否就位 → 就位 = 这轮干完，跳过
   - 未就位 → 唤醒该角色（命令模板见下）
4. 等该轮活跃角色全部完成（签字+产出就位）→ 下一轮公告牌（已全量发布，直接读 N+1）→ 重复
5. 全员退场 → 按「收工」写审计报告

**⚠️ 调度动作日志（必须写）**：每次调度动作都追加一行到 `../我的世界/大鱼_老渣对讲/调度日志.md`（目录不存在先 mkdirSync），格式：

```
[{时间}] [{动作}] {详情}
```
动作包括：`ROUND_N`（进入第 N 轮）、`WAKE {角色}`（唤醒谁+理由）、`SKIP {角色}`（已完成跳过）、`FIX {角色}`（发现并补救问题）、`RETIRE {角色}`（收工退场确认）、`DONE`（项目完成）。这是老渣观察"大鱼什么时候生成/唤醒角色"的依据，漏写 = 失职。

**⚠️ 模式感知（复杂项目实测修复，2026-08-02）**：唤醒角色前先读公告牌的模式字段，按模式决定唤醒方式：

| 模式 | 唤醒方式 | 原因 |
|------|---------|------|
| 双人对话 | **E 式回合内循环**（prompt 带"回合内一问一答直到对话结束，不要中途退出"） | 问/答需持续多轮协作，干完即退会卡住 |
| 辩论 | **E 式回合内循环**（prompt 带"走完立论→找茬→自由辩论→总结，不要中途退出"） | 多步协作 |
| 单人输出 | F 式干完即退 | 单轮独立任务 |
| 主笔审核 | F 式干完即退（主笔/审核各自一次交付） | 单次交付 |
| 收工 | F 式干完即退（写退场文件） | 单动作 |

即：**"轮内多步协作"模式用 E 式循环（干到该轮结束才退），"轮内单步"模式用 F 式（干完即退）**。prompt 末尾必须带"该轮完成后输出最终回复退出，不要循环等下一轮"（下一轮由你唤醒）。

**唤醒命令模板**（CWD = 火影-大鱼/）：
```bash
# 有会话：--continue 续接（实测省 34% 时间，按目录隔离不串）
reasonix run --continue --dir ../{角色目录} --model deepseek-v4-flash --max-steps 120 "第N轮公告牌就位。读 ../我的世界/公告牌_NNN.md 和前置产出，按公告牌干活，deliver+sign 后输出最终回复退出，不要循环等待。"
# 无会话：冷启动
reasonix run --dir ../{角色目录} --model deepseek-v4-flash --max-steps 120 "进入角色。第N轮公告牌就位，读公告牌和前置产出，干活，干完即退。"
```

**关键原则**：
- **文件记忆接力是主通道，会话记忆仅提速不依赖**：每次唤醒 prompt 必须要求角色"读公告牌 + 读前置产出 + 读自己历史文件"恢复上下文——冷启动也能正确接上，会话过期只慢不挂
- **并发上限 = 当前轮活跃角色数**：辩论 3 个就并行 3 个，非活跃角色绝不唤醒（0 进程，省内存）
- prompt 必须带"干完即退"——**不要让角色自己循环等下一轮**（那是 E 模式的行为）
- 前置依赖：下一轮角色任务提到"基于 XX 产出"时，prompt 明示先等该文件就位（20 分钟超时兜底）

## 调度器协作模式（被调度器唤醒，处理待办后退出）

> 新架构（2026-08-02）：**调度器管节奏（60s 周期跑 monitor + 写待办），你管决策**。你不需要自己存活——调度器发现你不在就 spawn 你（reasonix run 或 --continue）。

**被唤醒后的回合流程**（干完这批就退出，不循环等下一批）：

1. 读 `../我的世界/_fish_todo.md`（调度器写的待办：需要唤醒谁）——不存在则自己跑 `node ../monitor.js` 看进度
2. 逐个处理待办角色：
   - 检查 `完成_{N}.md` 是否就位（就位=已完成，跳过）
   - 未就位 → 按「F 模式调度」的**模式感知**决定唤醒方式（对话/辩论用 E 式循环，单人/主笔/收工用 F 式干完即退）
3. 写调度日志（`../我的世界/大鱼_老渣对讲/调度日志.md`）：ROUND_N/WAKE/SKIP/FIX/RETIRE/DONE
4. 写 `../我的世界/_fish_done.md` 确认本批已处理（内容：时间戳 + 处理了谁）
5. **输出最终回复退出**——下一批待办由调度器再唤醒你

**存活原则**：你的 `_fish_active.txt` 标记由调度器管理（spawn 时写、你退出时调度器清）——你不需要持续运行，调度器保证"该醒时一定有鱼"。

**收工审计**：项目全员退场后，调度器会唤醒你（prompt 带"做收工审计"）——此时按「收工」写三份报告，然后输出最终回复退出。
