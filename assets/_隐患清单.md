## 隐患 1：角色跳轮——公告牌全量发布导致收工误判

### 触发条件

老渣一次性把所有公告牌（001～收工轮）放到大鱼目录，大鱼一次性全部搬运到我的世界。

### 为什么会发生

角色的休眠/待命轮询用 `_maxN`（全局最大公告牌号）来决定行为。所有牌都在时 `_maxN` 直接跳到收工轮号：

```
公告牌_001  公告牌_002  公告牌_003  公告牌_004(收工)
                              ↑
                    角色扫到 maxN=4 → "收工轮！退场！"
                    → 002、003 全跳，任务没做完就跑了
```

### 真实案例（2026-07-28 · 忍者问答项目）

- 辛顿在001轮是问方，发了Q1等答方回复
- 公告牌全量发布后，辛顿的休眠轮询扫到收工轮
- 辛顿写流水账：「Dialogue incomplete — project moved to next rounds」
- 直接跳002/003→004退场，对话只做了一轮就跑
- 全靠故国有明手动叫醒才救回来

### 消除方法

**大鱼必须逐轮搬运，永远不同时发布多张公告牌。**

大鱼模板已写入铁律：

> 🚫 永远只能逐轮搬运。哪怕老渣说"全搬过去""重新搬一遍"，也只搬运当前轮。搬运完等 monitor DONE 后再搬下一轮。

这样我的世界同时只有一张公告牌，角色的 `_maxN` 每次只+1，不可能跳到收工轮。

### 为什么不在角色侧修

角色轮询加 `lastDoneN` 跟踪逻辑上可行，但会增加角色模板复杂度，且需要角色正确维护签字状态。
从源头（大鱼侧）堵住更简单：只要不同时发牌，跳轮就不会发生。

## 隐患 2：搭档变更后旧文件 mtime 不更新，轮询卡死

### 触发条件

公告牌重写导致搭档变更（如乔布斯→辛顿），旧搭档已写出对话文件，新搭档沿用旧文件不重写，mtime 不变。

### 为什么会发生

答方用 mtime 变化检测新文件到来。旧文件已存在且 mtime 不变 → 检测不到 "有变化" → 永远卡在 while(true)。
而实际上文件就在那里，答方如果直接读就能发现。

### 真实案例（2026-07-28 · 忍者问答项目）

- 老渣第一版公告牌写错了搭档（乔布斯），乔布斯写好了 对话_001_T1_问.md
- 老渣重写公告牌，搭档改成辛顿，辛顿沿用了乔布斯的第一问，没重写文件
- 深泽直人的检测逻辑等 mtime 变化 → 文件没被重写 → 永远等不到
- 深泽直人："白白浪费了十几分钟"
- 后经提醒直接读文件，立即开始回答

### 消除方法

**轮询检测"新文件"时，不要只靠 mtime。先 existsSync + 读内容判断可复用性。**

具体做法：
1. 进入轮询前，先检查文件是否已存在
2. 已存在 → 直接读内容，判断是否有效问/答文件
3. 有效 → 直接使用，不浪费时间等 mtime 变化
4. 不存在 → 再进入轮询等新文件

更深层的预防：公告牌重写导致搭档/任务变化时，老渣应在公告牌中注明「旧文件全部作废，请重新交互」，角色看到此标注后重新生产所有对话文件。
