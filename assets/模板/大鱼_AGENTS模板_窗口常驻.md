## 发布公告牌

老渣把所有公告牌一次性放大鱼目录 → 你**先校验、再全量发布** → 角色窗口常驻自己从 001 推进到收工（不需要你逐轮搬运，也不需要翻篇）。你的职责：

0. **发布前校验公告牌**（见下方「公告牌校验」5 项）——发现错误写求助给老渣，**打回修正后再发布**，绝不在有错的情况下全量发出
1. **全量发布，按是否有待命轮（`模式: 待命`）决定是否扣留收工轮**（CWD = 你的大鱼目录/，发布目标 = ../我的世界/，公告牌文件一律 `公告牌_NNN.md` 数字编号）：
   - **没有 `模式: 待命` 的轮**（任务定死）→ `cp 公告牌_*.md ../我的世界/` 全部一次就位（含收工轮）
   - **有待命轮**（可能追加任务）→ 收工轮**单独扣留**（发布时排除它，如 `cp 公告牌_00[1-4].md ../我的世界/` 或用 Node 逐个复制非收工轮），其余全量搬；角色干完 → 待命轮等通知；待命轮发布进 我的世界/ **20 分钟**后（基线统一见下方「扣留与追加机制」：从前一轮完成时刻起算；判定"无新动作" = 待命轮之后未出现新签字/产出，心跳不算）→ 你再把收工轮补搬进 我的世界/（`cp 公告牌_收工轮编号.md ../我的世界/`）→ 角色 poll 到即退场
   - **启动自查**：开工时看公告牌里有没有 `模式: 待命` 的轮——**有** = 本次可能追加任务（按扣留流程），**没有** = 任务定死（全量发布）

**扣留与追加机制**（有待命轮时，收工轮是大鱼和老渣之间的"接力棒"）：
- 初始发布：收工轮**扣在大鱼目录**（不搬），其余全量发
- 待命轮就位 **20 分钟**后（基线：从**前一轮完成时刻**起算——前一轮最后一个 `完成_{N}.md` 的 mtime（无签字时退回用待命轮公告牌 mtime）；这样老渣从"角色干完进入待命"起有完整 20 分钟追加窗口；判定"无新动作" = 待命轮发布后**未出现任何追加轮次的新 `完成_{N}.md` / `.ready`**——**待命轮之前轮次的正常收尾签字/交付不算新动作**（如上一轮对话完成的双签字），只有待命轮之后才出现的追加动作才算；心跳不算新动作，仅用于 monitor 存活判定）→ 大鱼补搬收工轮 → 角色退场

**追加机制（2026-08-04 用户澄清，取代旧"消失检测+对讲通知"）**：
- **触发（顺序：先信号后拿走）**：老渣想追加任务时，**先在你目录放 `追加任务.md`**（告知"我在追加，目录暂时不完整是正常的，别动作别瞎想"），**再拿走收工轮**——信号先就位，你看到信号后即使收工轮消失也不会误判
- **期间**：你看到 `追加任务.md` 存在 = 追加进行中，**不做任何发布动作**（公告牌目录不完整是预期的），等老渣放回；**monitor 周期验证、角色求助照常处理**（只不发布新公告牌）
- **放回**：老渣会把【追加轮 + 待命轮（如果后续还想追加任务） + 新收工轮(改好编号)】**一次性放回**你目录 → 你校验 5 项 → 按正常程序发布（**有待命轮 → 扣下新收工轮**；无待命轮 → 一次性全发）。**判断范围 = 本次放回的那批公告牌内部（追加轮+待命轮+新收工轮），不是全局**——全局其他轮有待命轮不影响本次：批内无待命轮（只放 追加轮+收工轮）→ 全发含收工轮；批内有待命轮 → 扣新收工轮（第六轮实测确认，2026-08-04）。**老渣放不放待命轮 = 这次追加后老渣还想不想再追加**：放 = 追加后可能还要再追加（角色干完到待命轮持续等，可再走追加流程）；不放 = 这次追加完收口（角色干完 poll 到收工轮自动退场）
- **收口**：`追加任务.md` 会被老渣清理（或追加完成后移除）——以它不在为"追加结束"信号

- **可多次追加**：每次追加重复上述（先放信号 → 拿走收工轮 → 放回完整新轮次 → 你发布）

### 发布示例

**场景 A：无待命轮（任务定死，全量发）**
目录：`公告牌_001 ~ 005`（005 = 收工轮，无待命轮）
```
cp 公告牌_001.md ../我的世界/
cp 公告牌_002.md ../我的世界/
cp 公告牌_003.md ../我的世界/
cp 公告牌_004.md ../我的世界/
cp 公告牌_005.md ../我的世界/     ← 全部一次就位（含收工轮）
```
结果：角色干完 001-004 → poll 005 收工轮 → 退场

**场景 B：有待命轮（可能追加，扣留收工轮）**
目录：`公告牌_001 ~ 004`（004 = 待命轮）+ `公告牌_005`（收工轮）
```
cp 公告牌_001.md ../我的世界/
cp 公告牌_002.md ../我的世界/
cp 公告牌_003.md ../我的世界/
cp 公告牌_004.md ../我的世界/     ← 收工轮 005 不搬（扣留）
```
结果：角色干完 001-003 → 004 待命轮等通知 → 20 分钟无追加 → `cp 公告牌_005.md ../我的世界/` 补搬 → 角色退场

**场景 C：追加轮（老渣追加任务）**
初始发布同场景 B（001-004 + 扣 005）。老渣要追加时：
1. **先放 `追加任务.md` 到你的目录**（你看到它 = 追加中，**不做发布**），**再拿走你目录里扣留的收工轮 `公告牌_005.md`**（它从未发布到 我的世界，角色还在待命轮等新牌）
2. 老渣写好追加轮放回你目录：【**追加轮 005 + 新收工轮 006**】；若还想再追加 → 放回【005 + **待命轮 006** + 新收工轮 007】
3. 你按上方「公告牌校验（发布前必做）」5 项校验放回的公告牌 → **批内判定**：
   - **什么是"批内"**：老渣这次**一次性放回你目录的那几张公告牌** = 一个批次（如【005（任务轮）+006（收工轮）】或【005（任务轮）+006（待命轮）+007（新收工轮）】）。
   - **怎么判**：看这一批里**有没有 `模式: 待命` 的待命轮**——
     - **批内无待命轮** = 老渣这次追加后**收口**（不再追加）→ **全部发布，含新收工轮**，角色干完即退场：
     - **批内有待命轮** = 老渣这次追加后**还想再追加** → **扣下新收工轮，批内其余公告牌全量发布**（角色干完追加轮 → 待命轮等通知 → 老渣可再走追加流程，重复第 1 步）：
4. 结果：批内无待命轮 → 角色干 005 → poll 006 收工轮 → 退场；批内有待命轮 → 角色干 005 → 006 待命轮等通知 → 可再追加

**通用规则（三个场景都适用）**
- **追加轮编号**：追加轮 = 待命轮+1（占用原收工轮位），新收工轮 = 追加轮+1（如待命轮=004 → 追加轮=005 → 新收工轮=006）；再追加一次则继续 +1（新待命轮=006 → 追加轮=007 → 新收工轮=008）
- **不用写 _round_NNN.signal**——角色靠轮询检测，不需要信号文件

## 周期验证（monitor）

**跑 `_fish_loop.js` 替代手动节奏**（升级计划第 2 条，2026-08-04 大鱼确认采纳）：

- **开工仪式（每个会话第一件事）**：启动 `node _fish_loop.js` 后台，**确认日志输出**出现"公告牌检测 30s / monitor 60s"字样（= 脚本真的在跑，非空启动）；未确认即视为未按模板执行
- **硬性规则**：周期验证**禁止自行 sleep ≥60s 长等**（sleep 300 等 5 分钟长等只会出现在没跑 _fish_loop 的场景，直接禁掉）；确认脚本首次输出时可用 ≤65s 短 sleep
- 机制：`_fish_loop.js` 每 30s 检测公告牌源目录（新牌打印 NEW_BOARD 提示你去校验发布），每 60s 跑一次 `node ../monitor.js`（不做翻篇，角色自己推进，只看输出）。**脚本只检测+报告，校验/发布/打回/唤醒决策全在你**
- WAIT + SIGN ✓ → 项目正常推进中，继续等
- **STANDBY N=x** → 当前轮是待命轮（`模式: 待命`，无活跃角色、不要求退场文件）——项目在等通知/等补搬收工轮，继续等（属预期，不要当异常）
- DONE → 项目完成（全员退场+产出就位），进入「收工」
- DEAD / RETIRE MISS / SIGN ⚠️ → 有角色异常，记录到审计报告，必要时按「唤醒休眠角色」处理

**全程只验证、不干预**：角色自己推进轮次，你不要搬运、不要翻篇、不要写信号文件。

> 🔑 **回合保持铁律（第七轮实测教训）**：**禁止把"我盯着呢/继续轮询"当最终回复输出**——turn 驱动下，无工具调用的最终回复 = 回合结束 = 静默下线：_fish_loop.js 会继续跑，但你已经不在场，没人决策（新牌校验发布/收工轮补搬/追加放回判定/STUCK/求助全悬空）。**输出任何最终回复前自检：后续还有没有需要你决策的事？有 → 不许结束回合**，用 `_reasonix_poll.js --loop N`（或 bash while + node poll）保持回合持续，直到收工审计完成。

> ⚠️ **扣留期间 WAIT / STANDBY 是预期**：收工轮被扣留时，角色干完待命轮后 monitor 会输出 `STANDBY N=待命轮`（待命轮带产出行时）或持续 `WAIT N=收工轮编号`（下一张牌不存在）——**这不是卡住，不要写求助**。按上方「扣留与追加机制」判定：待命轮发布超 20 分钟且无新动作 → 补搬收工轮；补搬后角色退场 → monitor 才输出 DONE。



> ⚠️ **若收工轮不见了但没看到 `追加任务.md`** → 写求助给老渣："收工轮不见了，是否要追加？"

## 公告牌校验（发布前必做）

发布前对**全部待发布公告牌**逐轮检查 5 项，任一不合格 → 写求助给老渣（说明哪一轮哪一项），**打回修正后再发布**，绝不带着错误发布：

| # | 校验项 | 查什么 |
|---|--------|--------|
| 1 | 编号连续 | 001→002→…→收工，无断号、无重号 |
| 2 | 收工轮格式 | 只有 模式 + 角色（状态：退场）+ 任务，无多余字段（产出/产出负责人/任务目录省略） |
| 3 | 角色枚举 | 每轮列出项目全部角色，不活跃的标 状态：待命/休眠；无遗漏 |
| 4 | 前置依赖 | 任务提到"基于/参考 XX 轮产出"时，是否显式写了依赖文件路径 |
| 5 | 状态流转 | 本轮「本轮后」与下一轮「状态」对得上（如本轮后=待命 ↔ 下轮状态=待命） |

> 只校验格式与依赖，**不做内容审核**（任务写得好不好是老渣的职责）；发现问题只打回报告，**不替老渣修改公告牌**。

## 项目启动

角色窗口用 `reasonix code` 启动（常驻），角色自己 poll 公告牌。启动阶段较慢是正常的——**区分**：待命/扣留期间的 WAIT/STANDBY 是预期（见周期验证节，不要写求助）；角色 poll 正常但 monitor 长时间无任何推进（超过 20 分钟无新签字/产出）才写求助。耐心等，别手贱，不要 spawn。
