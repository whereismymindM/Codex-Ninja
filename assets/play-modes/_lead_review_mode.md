# 主笔审核模式

一个人写（主笔）、一到多人审（审核方）。公告牌告诉你谁是主笔、谁是审核方、产出什么。

> 本文按**流程式**组织：每方先看「主干流程」（按执行顺序走），分支/异常（打回、超时、失联、多审核方）在下方独立小节——**主干走主线，遇到分支再翻对应小节**，不迷路。

---

# 一、主笔 · 主干流程

**1. 写产出**
按公告牌指定的产出路径和文件名把产出写出来。**先写内容，暂不调 deliver()**——等审核通过后再交付。

**2. 发 please-review**
- **单审核方**：任务目录下写 `please-review.md` → 写完**立即**写同名 `.signal`（原子两步，不得插入其他动作）
- **多审核方（≥2）**：给**每个审核方**各写一份 `please-review_{审核方角色名}.md` + 同名 `.signal`——各审核方等自己的信号、ack 自己的，**禁止共用单个 please-review.md.signal**

**3. 等审核结果**（用 wait_file.js，完整命令见「五、等文件工具」）
- **单审核方**：等 `review-result.md.signal` → 读到后读 `review-result.md` 内容
- **多审核方**：等**全部在审审核方**的 `review-result_{角色名}.md.signal`（wait_file 多目标 AND）→ 逐个读

**4. 处理结果**（逐份读第一行判断）
```
全部「状态：通过」（或通过+条件）→ 跳 5
任一「状态：不通过」→ 4a：读意见 → 改产出 → 4b：重发 please-review（见「分支·打回循环」）→ 回 3
```

**5. 交付并签字**
审核通过后，先交付再签字：
- **文档类产出**：fs.writeFileSync 确认最终版在 `../world/output/` → `node _deliver.js 文件名.md taskNNN` → `node _sign.js N`
- **代码类产出**：源文件原地改完 → `node _deliver.js 文件名.js taskNNN 源文件路径` → `node _sign.js N`

**.ready 在审核通过后才出现**——monitor 看到 .ready 即代表审核已通过。

**6. 看「本轮后」**
读公告牌你的「本轮后」：休眠 → 写流水账+休眠文件+低功耗轮询；待命 → --standby 轮询；活跃 → poll 下一轮。

---

# 二、审核方 · 主干流程

**1. 等主笔发 please-review**（wait_file.js）
- **单审核方**：等 `please-review.md.signal`
- **多审核方**：只等**自己那份** `please-review_{你的角色名}.md.signal`——**不要等/碰别的审核方的信号**

**2. 审产出**
认真读，不是走过场。读完立刻把 `please-review_{你的角色名}.md` 改名 `please-review_{你的角色名}_processed.md`（同名 .signal 已自动 ack；手写路径按后缀替换）——清旧防秒返。

**判据（三档，与公告牌统一）**：
| 档 | 定义 | 处理 |
|---|---|---|
| 🔴 必改 | 影响读者理解或执行正确性 | 必须打回 |
| 🟡 建议 | 可优化、不阻塞执行 | 主笔可拒改，但须在修订说明表注明理由 |
| ⚪ 存疑 | 不阻塞理解、可后续补充 | 标注「存疑：缺 XX 证据」即可，不阻塞通过 |

**🔑 验收轮（代码/可运行产物轮）**：审核方签字前必须确认**双过**——①静态审查通过 ②**实弹验证**已逐项跑过。
**代码/可运行产物轮默认需要实弹（至少能构建 + 主路径跑通）**——公告牌可声明实弹清单细化（如"node xxx 跑通""起服务发请求"）；公告牌未声明 = 按默认最小实弹（构建 + 主路径）执行，**不得因未声明而跳过**。
纯文档轮不需要实弹。**实弹验证由审核方执行或复核主笔提供的实弹记录（命令原文+输出原文，断言可复现）**。

**3. 给结果**（写 `review-result.md`；多审核方写 `review-result_{你的角色名}.md`）
第一行标状态，写完**立即**写同名 `.signal`：
- `状态：不通过` → 写清哪里不行、为什么、怎么改 → 回 1 等主笔重发
- `状态：通过` → 可附简短评价
- `状态：通过（附条件）` → 条件 = 必须在后续轮次/收工前落实的具体事项（如补数据、补实弹记录）——**不阻塞本轮交付签字**，但条件项要进流水账追踪

**审核意见 = 逐条核验格式**（建议结构化）：
```
编号 | 行号/章节 | 引用产出原文 | 判定（通过/不通过/存疑）| 建议改法
```
打回意见必须精确到"第几节/第几条/什么问题/怎么改"；不可判定项标注「存疑」。

**4. 签字**
`node _sign.js N`（禁止手写签字文件——铁律 6）。
> 🔑 **通过签字 = 审核职责完成**：在「状态：通过」上签字后，本轮的审核职责即尽，按「本轮后」正常退场/休眠——**不会有后续复审等你**（例外见「分支·微调修订 vs 实质修改」）。

**5. 看「本轮后」**（同主笔）

# 三、分支 · 打回循环

**重发对象（多审核方关键）**：
- 谁打回 → **只重发给打回方**（`please-review_{打回方角色名}.md` + .signal）
- **通过方已尽职责（终态）**：不参与复审、不重发、不再等它的信号——**等齐目标 = 未通过方**（修复：一份通过一份打回时，等齐打回方即可，不死等通过方）

**归档命名（防覆盖）**：
- 单审核方：`review-result.md` → 归档 `review-result_第N次.md`
- 多审核方：`review-result_{角色名}.md` → 归档 **`review-result_{角色名}_第N次.md`**（带角色名，两人同时打回不互相覆盖）
- 同名 `.signal` 一并处理（wait_file 已自动 ack；手写路径后缀替换）

**复审只核修订点（第 2 次起）**：
- 主笔重发时必须附**独立文件《修订说明_第N次.md》**（与 please-review 同批发送）
- 修订说明表格式：每条 = `原意见 | 修订位置 | 是否落实`（逐条对应审核方意见）
- **审核方第 2 次及以后的审核只逐条核对修订说明表**，不再全文重审（收敛打回循环，防"改 A 又挑出 B"发散）
- **修订可能引入新问题**：复审若发现修订触及未核范围或引入新缺陷，可指回（不算越界——"只核修订点"是默认，发现新增问题仍要提）

**打回 ≥3 次 → 写求助给大鱼**（`../world/{{ROLE_NAME}}_talk/fish-chat_NNN.md`，说明分歧点）——**不停止打回循环**，大鱼知情后可介入；打回次数不设硬上限。
**计数口径**：每审核方各自计数（`review-result_{角色名}_第N次.md` 的 N 按该角色自己的归档递增，不跨角色累计）——多审核方下各打回 1 次不算"累计 3 次"。

**打回循环联动失联**：若审核方心跳 stale 且无新文件（失联判据）→ 走「分支·超时/失联」的"视为通过"，不再"发→等满→再发"死循环。

# 四、分支 · 超时 / 失联

> 统一超时链（wait_file 超时 exit 2 后，_workflow.md 与本文共用）：
> ① 复查目标路径是否写错 → ② 查搭档心跳 + 对讲/output/任务目录近期文件（活着=还在干/在写，继续等）→ ③ 失联 = 写求助大鱼 + 补写 `_deadlock.md`（wait_file 超时不自动写，手动补，通知 monitor 尝试唤醒）→ ④ 先干不依赖部分 → ⑤ 按角色侧规则收尾

**主笔等审核超时**：
- 查审核心跳 + 近期产出 → **活着 = 继续等**（重新 wait_file 加长超时）
- 失联 = 写求助大鱼 → **按"视为通过"处理**：自己复核一遍产出（自己是第一道关卡）→ deliver + 签字 → 流水账标注"审核失联，主笔自审后交付"
- 产出可能带未审风险，收工审计可标红提示；`.ready` 附注标注"审核失联，主笔自审后交付（未过审）"

**审核方等主笔超时**：
- **先查主笔状态，两种都算活着 → 继续等（重新 wait_file 加长超时）**：
  ① 心跳活（只是慢/还在写）
  ② **心跳 stale 但对讲/output/任务目录有近期新文件（长回合写文件/长思考没续心跳——与 monitor 宽容判据同源）** ← P1 补分支：心跳静默 ≠ 失联
- **只有心跳 stale 且无任何近期产出 = 失联** → 写求助大鱼 → 审核**不代写产出**（产出归主笔）→ 跳过签字 → 流水账标注"主笔失联，审核未签"（**审计豁免凭据**，收工审计不标红）
- 产出缺失由 monitor `WAIT_OVERDUE` 兜底报警

**"视为通过"后打回到达**：主笔自查复核 → 确有问题则修订并**重新 deliver** → 流水账标注"超时后打回到达，已修订重交"；签字不撤销（签字 = 本轮交付记录）。

**掉线恢复续接**：休眠/退场角色 poll 到新文件不会自动醒——需 monitor 心跳机制/大鱼 `_wakeup.js` 唤醒；恢复后查 `please-review_{自己}` 当前状态：主笔已交付签字 → 补审签字+一句补审意见退场；主笔仍在打回循环 → 从当前 please-review 续审。

# 五、等文件工具

**优先用 `wait_file.js`**（自动续心跳 + 自动 ack + 失联检测）。完整命令（复制即用，替换 NNN/XXX 和角色名）：

```bash
# 单审核方·主笔等结果
node temp-scripts/wait_file.js ../world/taskNNN_XXX/review-result.md.signal --timeout 20
# 多审核方·主笔等全部（AND 语义，全部就位才返回）
node temp-scripts/wait_file.js ../world/taskNNN_XXX/review-result_审核方甲.md.signal ../world/taskNNN_XXX/review-result_审核方乙.md.signal --timeout 20
> ⚠️ 示例里的"审核方甲/乙"只是占位——**必须换成公告牌上的真实角色名**（如 reviewer-a），照抄字面量 = 审核方永远等不到信号
# 审核方等请审
node temp-scripts/wait_file.js ../world/taskNNN_XXX/please-review_你的角色名.md.signal --timeout 20
```

> **路径规则**：任务目录 = `../world/taskNNN_XXX/`（相对角色目录的全路径，NNN=轮号、XXX=任务名，与公告牌一字不差）。`--hb` 可省略（wait_file 自动推导角色对讲目录续心跳）。多审核方监控失联：`--watch-hb` 单参数只能监控一个心跳，其余靠超时后查心跳兜底。

**内联 fallback**（仅当 wait_file 不满足需求时手写；CommonJS 同步版，**禁止顶层 await**）：

```js
// 等一个文件出现——CommonJS 同步版。替换 YOUR_FILE_PATH
const fs = require("fs");
const { execSync } = require("child_process");
var _deadline = Date.now() + 20 * 60 * 1000;
var _hbCtr = 0;
while (true) {
  if (fs.existsSync("YOUR_FILE_PATH")) break;
  if (++_hbCtr % 60 === 0) {
    var _hbPath = "../world/{{ROLE_NAME}}_talk/_heartbeat.txt";
    fs.mkdirSync(_hbPath.substring(0, _hbPath.lastIndexOf("/")), { recursive: true });
    fs.writeFileSync(_hbPath, String(Date.now()), "utf8");
  }
  if (Date.now() > _deadline) {
    var _dlDir = "../world/{{ROLE_NAME}}_talk";
    fs.mkdirSync(_dlDir, { recursive: true });
    fs.writeFileSync(_dlDir + "/_deadlock.md", "timeout", "utf8");
    var _logName = _dlDir.split("/").pop().replace("_talk", "");
    fs.appendFileSync(_dlDir + "/" + _logName + "_poll-log.md", "[" + new Date().toISOString().substring(11,19) + "] 等文件超时 已写_deadlock\n", "utf8");
    break;
  }
  execSync("sleep 0.5", { stdio: "ignore" });
}
```

> ⚠️ **手写骨架纪律**：等 `.signal` 就位后**必须手动 ack**（rename 后缀 `_acked`/`_processed`）；写方写完 `.md` 的下一动作必发同名 `.signal`（漏发 = 读方 wait_file exit 5 中断）。**禁止 bash 长等**（heredoc 挂死教训）。

# 六、多审核方协议（汇总）

- **主笔发**：`please-review_{审核方角色名}.md` + 同名 .signal（按审核方分别发）
- **审核方写**：`review-result_{自己的角色名}.md` + 同名 .signal（写完立即发，原子两步）
- **主笔等**：等**未通过方**全部 signal（wait_file 多目标 AND）——通过方终态不再等
- **打回重发**：只重发给打回方
- **归档**：`review-result_{角色名}_第N次.md`（带角色名，防覆盖）
- **独立审核**：允许审完互看结果，但**不得先读对方结论再动笔**

# 七、微调修订 vs 实质修改（通过后复审的例外）

**默认**：v1 通过即最终通过——审核方通过签字后职责尽，主笔后续修订（v2+）为**自审确认**，不再发三方复审；禁止通过签字后再发 please-review 等已退场审核方。

**例外**：审核方签字时可显式声明"**通过，但限定修订范围 = X**"；主笔修订**超出该范围**（或动了审核方通过所依赖的关键判定）→ **必须重发** `please-review_{该审核方}` 请其复核。

> 🔑 **限定范围 = 双向承诺**：审核方声明限定范围 = **承诺会回来复核**（签字后不立即退场/休眠，或至少保持 poll）；主笔承诺修订**不超范围**（超范围才重发）。**审核方声明限定范围后按「本轮后」待命/休眠的，重发请审时主笔先查其 poll-log**——不在轮询 = 只能用户唤醒（见唤醒边界），主笔须写求助大鱼转告用户，不得干等已退场审核方。

# 八、语言规则与注意

- 产出和审核意见**默认中文**；公告牌、代码注释保持中文
- 产出路径必须与公告牌一字不差（少一个字 = monitor 找不到 = 白干）
- 生成真实内容，别写占位符
- 可以多轮打回直到满意（打回 ≥3 次写求助大鱼，不停止循环）
