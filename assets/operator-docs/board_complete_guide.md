# 公告牌完全指南

> 读者：老渣（人，使用 Skill 的编排者）| 一份文件学会写公告牌——格式、状态机、多轮规划、常见错误，全在这里。

> 💡 **赶时间/照抄？** 用 `board_standard_template.md`（骨架 + 硬标准 + 各模式怎么填 + 协作角色行示例 + 补充定义）——不用读本指南全文。**本指南是"为什么"，标准模板是"怎么抄"**：先抄对（模板），再懂原理（指南）。

## 一、公告牌是什么

公告牌是你和项目之间的唯一接口。你写什么，项目就跑什么。大鱼不改一字搬运，角色逐行解读执行，monitor 全自动检查。

一个公告牌 = **一个独立文件** = 一轮任务。

**文件命名必须是 `board_NNN.md`**（NNN=3位补零，如 `board_001.md`、`board_002.md`）。全部放大鱼目录（`fish/`）下，大鱼校验后全量发布到 world/，不改一字。

> 🎯 **别称 vs 落地名**：任务轮/待命轮/收工轮/调查轮都只是**交流别称**——落地文件名一律 `board_NNN.md`。例：待命轮落地 = `board_002.md`，收工轮落地 = `board_003.md`。别称不进文件名、不进格式。

> 🚨 **禁止多轮写进同一个文件！** 大鱼按 `board_001.md` → `board_002.md` → … 编号逐个发布。一个文件塞多轮 = 编号不连续 = 大鱼校验打回 = 项目卡死。

> 💡 **通用公告牌**：**老渣的标准化模板集**（`通用公告牌/`，README 索引）——待命轮/收工轮/调查轮×7（文件读取/第一原则/排版/工具/协作体验/时间卡点/唤醒疑惑）+ 流程体验报告 + AGENTS 自检 + 老渣对讲公告牌，每种一个 .md 模板，复制后改编号/角色名/路径即可用。
>
> **它是干嘛的**：把高频轮次做成**填空式模板**，老渣写公告牌时不用每次从头写——挑模板 → 落地改名 `board_NNN.md` → 填内容 → 放大鱼目录。测试和生产都用。

## 二、基本格式

NNN=3位补零（如001、002）。

> ⚠️ **铁律：每轮公告牌必须列出项目的所有参与人员，不管本轮是否活跃。** 不活跃的标 `状态：休眠` 或 `状态：待命`。漏写任何人 = 那个角色收不到任何信号 = 可能误判项目结束而退场。

```
# 公告牌 第NNN轮
🔒 第一原则：最后一个动作必须是工具调用，不能纯文字下线；poll 到收工轮才合法退场
- 产出类型: [文档 | 代码]
- 模式: [双人对话 | 主笔审核 | 辩论 | 单人输出 | 试用 | 待命 | 收工]
- [角色名]（角色：[问方|答方|主笔|审核|正方|反方|裁判|单人]，搭档：[搭档名]，状态：[活跃|待命|休眠|退场]，本轮后：[休眠|待命|活跃]）
- [角色名]（状态：[活跃|待命|休眠|退场]，本轮后：[休眠|待命|活跃]）
- ⚠️ 警告: [可选，本轮临时约束]
- 任务: [大白话写清楚谁干什么、产出什么、放哪]
- 产出负责人: [角色名]
- 产出: world/output/taskNNN_XXX/文件名.md
- 任务目录: world/taskNNN_XXX/
- 交付参数: taskNNN_XXX（**deliver 第 2 参 = 纯目录名，不带 world/output 前缀**——`产出:` 是 monitor 按字面查的完整路径，不是 deliver 参数；写牌时务必三行都填，角色靠它省一步换算）
```

> 📌 **taskNNN_XXX 子名建议 ASCII**：XXX（任务名）建议用英文/拼音（如 `task001_req`、`task002_review`），不要用中文——千问等模型拼路径时中文易出错。用中文子名也能跑（monitor 按字面匹配），但千问写牌/拼路径时可能踩坑。

> 说明（不进公告牌，仅老渣看）：
> - **玩法文件** = `assets/play-modes/` 下按模式分发的 4 个模式文件（_dual_chat_mode.md/_lead_review_mode.md/_debate_mode.md/_solo_output_mode.md）——scaffold 复制到每个角色目录；角色按「模式」字段读对应玩法文件执行流程，公告牌任务文字不需要重复玩法细节
> - **任务轮里的待命角色**：写 `状态：待命`；仅**待命轮**（`模式: 待命`）的角色行才写 `状态：待命，等通知`
> - **多人同职位**：每实例一行角色行（如 `- 码农-张三（状态：活跃）` + `- 码农-李四（状态：活跃）`）——协议只认角色行实例名（签字/退场/output按实例走）；任务描述点名分工仅作说明；模板占位符写职位草稿（`{码农}`），编排时展开实例
> - **警告栏** = 本轮临时约束的唯一通道——角色模板铁律管"全局通用约束"，警告栏管"只本轮适用的特殊要求"（禁止某操作/编码坑/依赖前置/特殊流程/临时规则）；角色 poll 到第一眼必读

> **🔒 第一原则行是固定行（模板自带，老渣不用手写）**：每张公告牌都带，角色读牌第一眼看到。它是"提醒"不是"教学"——第一原则的完整定义在角色 AGENTS.md，这里只刷新记忆。

## 三、核心字段速查

| 字段 | 必填 | 写错了会怎样 |
|------|:--:|-------------|
| 产出类型 | 收工轮、待命轮不需要 | 收工报告归类错误 |
| 模式 | 是 | 角色走错玩法 |
| 角色名（状态, 本轮后） | 是 | 角色行为随机 |
| 列出全部参与人员 | 是 | 漏掉的成员收不到信号，可能误退场 |
| 任务 | 任务轮**必填**；收工轮**建议填**（monitor 不校验、不填不卡死，但它是角色收工步骤的直接指令——不填 = 角色全靠模板自觉、容易忘；标准文本见 `board_standard_template.md`「收工轮任务栏」）。goal 模式批次的任务栏逐字稿见 `goal_mode_guide.md` 四 | 任务轮漏写 = 产出对不上预期 |
| ⚠️ 警告 | 半硬（不解析但必读） | **本轮临时约束的唯一通道**——角色模板铁律管全局，警告栏管"只本轮适用"：禁止某操作/编码坑/依赖前置/特殊流程/临时规则。**角色模板里没有的约束，都从这里下达**；无警告栏 = 本轮无特殊注意（角色不要自己加戏）；收工轮不需要 |
| 产出负责人 | 是（**多人同职位共产出用 `各自`**——monitor 校验每个活跃角色都有带自己 `producer:` 的 `.ready`，一人重复交付凑数判不过；单人用实例名）；**收工轮、待命轮不需要** | 收工报告追责链断了 |
| 产出 | 是（`各自` 时格式 B 目录必须用尾斜杠 `output/taskNNN/`——monitor 校验每个活跃角色都有带自己 `producer:` 的 `.ready`（归属校验，只数数量会被一人重复交付凑数）；`角色名` 时保持任一 .ready 即完成）；**收工轮、待命轮不需要** | monitor 死等不存在的路径 |
| 任务目录 | **收工轮、待命轮不需要** | 角色不知道去哪交换文件 |
| 辩论轮数 | 可选（辩论模式；**不写 = 自由发挥**，任一方写 `debate-end.md` 即收敛；写 = 设上限） | 写错不会卡死，只影响上限 |

状态值：`活跃`=干活，`待命`=等通知（可能追加，别走），`休眠`=低功耗（只等唤醒/收工），`退场`=收工轮终局。
本轮后：`休眠`=写休眠文件+切高频，`待命`=切慢轮询（--standby），`活跃`=准备接棒。

## 四、状态机

写公告牌最难的不是格式，是角色状态在轮次间的流转：

```
  待命 --> 活跃 --> 本轮后：待命 --> 待命（继续poll）
   |        |
   |        +--> 本轮后：活跃 --> 活跃（下轮接着干，连续轮）
   |        |
   |        +--> 本轮后：休眠 --> 休眠（写slept_NNN，低功耗poll）
   |                                      |
   |                              被唤醒 --> 活跃
   |
   +-- 待命中被唤醒 --> 活跃（大鱼 _wakeup.js 对所有状态生效）
   |
   +-- 休眠中检测到收工公告牌 --> 写 {角色名}retired_NNN（终局）
   |
   +-- 全程待命 --> 收工轮 --> 写 {角色名}retired_NNN（终局）
```

三条铁律：
1. **休眠只写一次（除非被唤醒）**。002 休眠写 slept_002，003/004 延续休眠不再写。
2. **本轮后和下一轮状态必须对得上**。反过来推：先想每轮谁干活，再倒推本轮后。
3. **待命不是休眠**。待命=随时接棒，休眠=只等唤醒/收工。
> **判定口诀**：写「本轮后」时问一句——"**后面可能还有你 → 待命；确定没你 → 休眠**"。可能追加/可能还有轮次 → 待命（自己在等，随时接棒）；确定后续没这角色的活 → 休眠（只等唤醒/收工）。**别把休眠当"省资源的待命"**——休眠角色不主动接新任务，追加时需大鱼唤醒，多一层依赖；省的那点轮询开销（token 不多）不值当。

> 🔑 **两个"待命"别混**：①**本轮后：待命** = 角色行里的字段，表示"这个角色干完这轮后转入待命节拍"；②**模式: 待命** = 公告牌模式，表示"这一整轮是待命轮（全员等通知）"。前者是角色级流转，后者是轮级类型——一个角色"本轮后：待命"≠ 这轮是待命轮。扣留收工轮只看 `模式: 待命`（轮级），不看角色行字段。
> 🔑 **待命写法区分（老渣写牌）**：**待命轮**（`模式: 待命`，整轮就是等通知）的角色行写 `状态：待命，等通知`（带"等通知"，强调"后面可能追加，别走"）；**任务轮里状态为待命的角色**（这轮没他事、但整轮是干活轮）只写 `状态：待命`——不带"等通知"。

> 🔑 **休眠角色追加要唤醒（写牌决策）**：标了"确定没你 → 休眠"的角色，**就算后面插了待命轮也不会被唤醒**（休眠角色只等收工/唤醒，不接新任务牌）——追加时要靠大鱼 `_wakeup.js` 主动唤醒。所以"休眠"只在确定后续无你时用，别当省资源的待命。

### 待命轮 vs 收工轮（决定角色收尾行为）

**角色看到最后一张公告牌后的行为，取决于大鱼发布到 `world/` 的公告牌里最后一张是什么**（角色 poll 的是 `world/board_NNN.md`，不是你的源目录；收工轮被大鱼扣留时，发布里的最后一张 = 待命轮）

| 大鱼发布的最后一张牌 | 角色行为 |
|---|---|
| **待命轮**（`模式: 待命`，全员 `等通知`）| **持续轮询等待新任务通知**——不下线、不退场，随时可被追加任务唤醒 |
| **收工轮**（`模式: 收工`，全员退场）| **写退场文件，退场**——不再 poll，回合结束 |

> 待命轮 = 告诉角色"别走，可能还有活"；收工轮 = 告诉角色"干完了，下班"。

**你写牌规则（待命轮放哪、什么时候放）：**

- **写牌时最后一轮永远是收工轮**（你写的公告牌序列最后一张 = 收工轮）
- **可能要追加** → 在收工轮**前一张（倒二）放待命轮**：`任务轮 → 任务轮 → ... → 待命轮 → 收工轮`
- **确定不追加** → 不放待命轮：`任务轮 → ... → 收工轮`
- **追加轮同样进状态矩阵**：追加轮 = 矩阵加一列，按「十、任务编排」第 3 步画法核对流转（谁活跃、本轮后、与下轮衔接）——**别只加公告牌不加矩阵**，矩阵是校验状态流转的总账
- **什么时候放待命轮**：**你觉得后面可能还要追加任务时**（项目可能继续、需求可能变）；确定收尾就不放（角色干完看到收工轮自动退场，省资源）

**收口**：有待命轮时，大鱼会扣留收工轮暂时不发，将其余公告牌（含待命轮）一次性发往角色们的工作目录（world），角色做完任务后会在待命轮等通知，而不是下线或退场。
**公告牌发布后、角色退场前，老渣随时可追加**（角色在任务轮/待命轮都在线，全程可追加）。其中补搬触发点：
**待命轮前一轮最后一个签字落盘时刻**（基线：所有 `done_NNN.md` 取最后一个 mtime）起 **10 分钟**到点仍无追加 → 大鱼补搬收工轮 → 角色退场 → **退场后追加关闭，过了就追加不了**。
无任何签字时基线退回**待命轮牌发布时刻**（world/ 里已发布的待命轮公告牌 mtime = 批次启动时刻，不是源目录那份）。

**追加机制**：你要追加任务时：①**写好追加轮**公告牌 → ②**先放大鱼目录 `追加任务.md`**（告知大鱼"追加中，目录不完整是正常的"）→ **再拿走收工轮**（收工轮此时仍在大鱼目录，被扣留未发布；信号先就位，收工轮消失不误判）→ ③把【追加轮 + 待命轮（如果后续还要追加任务则放） + 新收工轮(改好编号)】**一次性放回**大鱼目录 → ④大鱼校验后按正常程序发布。
**判断范围 = 本次放回的批次内**（非全局）：批内有新待命轮 → 扣新收工轮；批内无待命轮（只放 追加轮+收工轮）→ 一次性全发（含收工轮）。
**待命轮放不放 = 这次追加后还想不想再追加**：放 = 追加后可能还要再追加（角色干完到待命轮持续等，可再走追加流程）；不放 = 这次追加完收口（角色干完 poll 到收工轮自动退场）。`追加任务.md` 被清理 = 追加结束。可多次追加。

## 六、产出路径写法

monitor 根据产出行的写法自动切换两种检查模式：

**格式A（推荐）：带文件名**
```
- 产出: world/output/task001_engine/server.js, search-engines.js
```
monitor 在产出目录下逐项检查 `server.js.ready` 和 `search-engines.js.ready`。deliver() 交付时自动在同目录生成 .ready 信号——两者一一对应。全部 .ready 就位才判定通过。

**格式B：仅目录名**
```
- 产出: world/output/task001_engine/
```
monitor 在产出目录下扫描，存在任意 .ready 文件即通过。

> **代码/源码类产出（约定）**：源码（.js/.py 等）写 `world/src/{角色名}/`——不是 output！
> monitor 深扫已支持 src（按目录归属追踪角色活跃，防长回合写码误判 DEAD）。
> **每轮交付物仍是 output 的 .md（验证证据/自测记录/验收报告）+ .ready**（.ready 判定轮次完成）。
> 任务写法：`源码 → world/src/{角色名}/，交付物 → 产出: world/output/taskNNN_xxx/验证记录.md`。
> 代码走 src 的原因：代码是持续演进的（同一文件多轮改），output 的"一次交付"语义与代码演进冲突；src 目录归属唯一（防共享区活动掩盖真死）。

> **产出路径必须指向 deliver() 写入的产出目录（即 `world/output/taskNNN_XXX/`）。**
> 指向源文件所在目录（如 `world/源代码/`）会导致 monitor 先去错误位置找 .ready，找不到再走兜底扫描 `output/` 子目录（⚠️ 仅格式 A 场景；格式 B 无兜底）。能跑通，但多一次扫描——正确路径直接命中，判定更快。

多个产出目录用多行写：
```
- 产出: world/output/task001_frontend/index.html
- 产出: world/output/task001_backend/server.js
```
### 产出类型：代码 vs 文档

你写产出路径之前，先判断本轮产出属于哪种类型——这决定了角色怎么交付、monitor 怎么检查：

| | 代码类产出 | 文档类产出 |
|---|---|---|
| **场景** | 修改已有源文件（如 `源代码/extractImports.js`） | 从零新建（报告、设计文档、裁判结论等） |
| **公告牌产出路径** | world/output/taskNNN_XXX/文件名（指向信号位置） | world/output/taskNNN_XXX/文件名（文件+信号都在这） |

> **公告牌的产出路径永远写 world/output/taskNNN_XXX/。** 不管代码类还是文档类——信号都在这里。角色交付方式（deliver/源文件原地改等）见角色文档，老渣写牌只需记这一条。

## 八、容错机制（使用者须知）

多角色协作中搭档可能掉线。系统有三层容错：

1. **心跳自愈**：角色轮询自动写心跳，monitor 检测到心跳超时自动写唤醒文件（机制细节见角色文档）。
2. **死锁并行处理**：等搭档文件超时（20 分钟）——**主笔审核**：写 `_deadlock.md` 通知 monitor 尝试唤醒搭档，但自己不卡等，跳过缺失步骤继续推进；**双人对话**：复查路径 → 查搭档心跳 → **写求助给大鱼**（不再手写 `_deadlock.md`，_deadlock 降级为 monitor/脚本内部信号，角色不手动管，见玩法文件统一口径）。
   **辩论除外**——裁判是天然兜底，辩论超时不写 `_deadlock.md`，只 break 继续。裁判即使只拿到一方材料也能给结论。

3. **产出兜底**：monitor 推进判定不看签字只看产出就位——签字不阻塞推进，但**角色必须签字**（收工审计的逐轮完成矩阵会核对签字文件，缺失标红）。

> 💡 这意味着你设计多轮方案时，可以放心用双人模式——搭档掉线不会卡死整轮。

## 九、常见错误

1. **已经休眠的角色重复写本轮后**——休眠状态不需要本轮后，角色已经在低功耗 poll 了。
2. **本轮后跟下一轮状态对不上**——002 轮说干完待命，003 轮却是退场。
3. **收工轮写了产出和任务目录**——monitor 只看退场文件。**唯一豁免**：角色心跳超时（窗口 2 分钟/run 10 分钟）且超时窗口内无本角色新产出 = 真死或干完即退，monitor 按 `hbForce` 视为已退场放行 DONE（不要求退场文件，判据见 monitor.js `_hbForceRetired`，主判断/自检/回看三处同源）。
4. **忘写产出负责人**——monitor 不报错但收工报告追责链断了。
5. **任务描述里出现角色名（状态：活跃）格式**——已不构成实际风险（monitor 用 headerPart 限定扫描区，任务描述不再被误抓）。
6. **产出路径没从 world/ 开始**——产出正则要求 `产出: world/...` 前缀，无前缀**完全匹配不到**（outputCount=0）→ 活跃轮永久 WAIT，**没有 fallback**。务必按模板写 `产出: world/output/...`。
7. **辩论轮数写错不会卡死**——轮数是**可选字段**：不写 = 自由发挥（任一方写 `debate-end.md` 即收敛，角色不会"停不下来"）；写 = 设自由辩论上限。**不写不是错误**（辩论模式机动性强，自由发挥优先）。
8. **双人对话没区分谁问谁答**——只有问方能写 `chat-end.signal` 喊停，角色字段里必须标注。
9. **多轮写进一个文件**——大鱼只按文件名 `board_NNN.md` 发布，一个文件塞多轮 = 项目卡死。每轮必须独立文件。
10. **漏写非活跃角色**——每轮必须列出项目全部参与人员，不管本轮是否干活。漏写 = 角色收不到信号 = 可能误退场。

## 十、任务编排（最难的部分，先想清楚再写牌）

> **写公告牌不难（填空即可），难的是编排**：怎么把任务拆成轮、每轮用什么模式、角色状态怎么流转、依赖怎么串。编排错了，格式再对也白搭。以下六步，每步都想清楚再写牌。

### 第 1 步：拆轮（任务 → 几轮）

拿到任务先问：**这个任务能拆成几个独立交付？** 每轮 = 一个可验收的产出（文档/代码/结论）。

| 拆轮依据 | 例子 |
|---|---|
| 产出类型不同 → 拆 | 需求文档 / 系统设计 / 代码 / 测试报告 → 4 轮 |
| 依赖关系 → 拆 | 先有需求才能设计，先有设计才能编码 → 串行拆 |
| 一个产出需要多人协作 → 合并 | 需求讨论（双人）+ 方案（主笔审核）可能合不了一轮 |
| 相互独立 → 可并行（但公告牌是串行的，并行靠角色待命轮等通知） | 前端/后端可拆两轮（前后接力） |

**原则**：轮数 = 交付物的数量，不是步骤的数量。每轮结束都该有"东西落地"（output/签字）。**每轮交付物需可验收**：单一类型（文档/代码二选一）、可检查、有完成定义（如"文档含 xx 节""代码可运行"）——拆不出来验收标准 = 这轮拆得不对。

### 第 2 步：定模式（每轮用哪个玩法）

按每轮的**协作性质**选模式：

| 每轮要做什么 | 模式 |
|---|---|
| 一个人独立产出 | 单人输出（**产出前先终审自检**：逐条验证/标存疑/补遗漏，见 `_solo_output_mode.md`「终审 pass」） |
| 需要深挖/澄清（需求访谈、方案探讨） | 双人对话（问方挖、答方答，产出归问方） |
| 一个人写、另一个人把关 | 主笔审核（主笔写、审核审，通过才交付；**审核意见逐条核验**） |
| 两个对立方案、需要裁决 | 辩论（正方/反方/裁判；**裁判结论逐条核验双方论点**） |
| 收集反馈/自检 | 工具轮（通用公告牌：调查轮/流程体验/自检） |
| 真人实际点一遍交付物、收反馈修缺陷 | 试用轮（真人试用→反馈清单→角色修→trial-report→deliver+sign；区别=真人亲手操作交付物，AI 自审审不出体验问题。填写说明见 `board_standard_template.md`「试用轮」） |
| 等通知/可能追加 | 待命轮（放收工轮前一张） |
| 结束 | 收工轮（永远最后） |

### 第 3 步：画状态矩阵（核心中的核心）

**先画表，再写牌**。表 = 谁、哪轮、干什么、干完去哪。列 = 轮次，行 = 角色，格 = `状态->本轮后`。

```
| 角色 | 001 | 002 | 003 | 004(收工) |
|------|-----|-----|-----|-----------|
| 角色A | 活跃->待命 | 活跃->休眠 | 休眠 | 退场 |
| 角色B | 待命 | 活跃->休眠 | 休眠 | 退场 |
| 角色C | 待命 | 待命 | 活跃->休眠 | 退场 |
```

画法：
1. **先填活跃**：每轮谁干活（按第 1、2 步的拆轮和模式）
2. **再推本轮后**：这轮干完，下轮有没有他？有 → 待命（随时接棒）或活跃（下轮接着干）；确定没有 → 休眠
3. **核对流转**：本轮"本轮后"必须 = 下轮"状态"（本轮后待命 ↔ 下轮待命）
4. **收工轮全员退场**：最后一张所有角色 状态=退场

> ⚠️ **判定口诀**：后面可能还有你 → 待命；确定没你 → 休眠。别把休眠当"省资源的待命"（休眠角色不主动 poll 新牌，追加时要唤醒）。

### 第 4 步：串依赖（轮间怎么接）

轮与轮之间靠**产出传递**。规则：
- **依赖必须显式写路径**：任务描述里写"读 `output/task001_req/需求文档.md`，然后……"——不写 = 角色可能不等直接干 = 产出对不上
- **路径写真实位置**：写牌前确认依赖文件当前在哪（可能被移过）；历史素材可能被移入 `_回收站/…` 或归档目录——写牌前 `ls output/` 核对文件真实在册，"归档位置"与"依赖本体位置"分开标注
- **任务描述不覆盖玩法文件路径**：辩论/双人等中间文件路径以玩法文件为准，任务描述只写产出清单（否则路径分叉卡死）

### 第 5 步：定收尾（收工前要不要待命轮）

| 情况 | 怎么收尾 |
|---|---|
| 确定不追加 | 任务轮 → … → **收工轮**（角色干完直接退场） |
| 可能追加（需求可能变/后续可能加轮） | 任务轮 → … → **待命轮** → 收工轮（角色在待命轮等通知，给你追加窗口） |

> **待命轮放不放 = 你后面还想不想追加**。放 = 告诉角色"别走，可能还有活"；不放 = 任务定死直接收工（省资源）。

### 第 6 步：自查（写完每张牌对着状态矩阵核对）

- [ ] 每轮的活跃角色 = 状态矩阵里的"活跃"？
- [ ] 本轮后 和 下一轮状态 对得上？
- [ ] 依赖轮次写了完整产出路径？
- [ ] 收工轮是最后一张、全员退场、只写 模式+角色+任务？
- [ ] 可能追加 → 有待命轮；确定收尾 → 无待命轮？

> 公告牌就是代码。角色 Agent 逐行解析，没有中间态。写完之后对着状态矩阵逐条核对。
> 多轮编排思路参考 `example_RSS_digest.md`（⚠️ 历史示例，只学编排思路，字段以标准模板为准）。

### 第 7 步（可选）：用 compose.js 自动编排

> **手工编排最容易错的是状态矩阵和流转**（画错 = 角色卡死）。`scripts/compose.js` 把"填 JSON 配置 → 自动生成公告牌 + 状态矩阵 + 流转编译期校验"：

```bash
node <skill路径>/scripts/compose.js <编排.json> [输出目录]
# 例：node compose.js 编排.json fish/
```

- **输入**：JSON 配置（角色名单 + 轮次计划：模式/角色/任务/output）
- **输出**：`board_001.md ~ NNN.md`（可直接放大鱼目录）+ 状态矩阵 + 校验报告
- **自动做**：编号/文件名、状态矩阵推导、**流转编译期校验**（本轮后 ≠ 下轮状态 → 报错不生成）、按模式生成角色行（辩论→正方/反方/裁判+搭档；双人→问方/答方）、收工轮自动（5 步任务栏）、格式硬标准（产出前缀/占位符/角色枚举/收工字段省略）
- **配置格式示例**（详见 compose.js 头部注释）：
```json
{ "项目": "XX", "角色": ["A", "B", "C"],
  "轮次": [
    { "模式": "辩论", "角色": {"A": "正方", "B": "反方", "C": "裁判"},
      "任务": "论题……", "产出负责人": "C",
      "产出": "world/output/task001_XX/结论.md",
      "任务目录": "world/task001_XX/" },
    { "模式": "收工" }
  ] }
```
- **原则**：compose.js 生成的牌 = 手写的牌（同格式同标准）；手工编排仍可用，compose 是"防矩阵画错"的辅助，不是替代——复杂/非常规轮次仍建议手写 + 过一遍「十、任务编排」第 6 步核对清单。
- **流程模板库**：`scripts/templates/` 下有 20 个**现实团队流程模板**——`full_software_lifecycle`（需求定义→评审→架构→契约→开发→测试→发布决策→复盘，接力型）、
  `four_phase`（拆缝→测试基线先行→做肉→拼缝→试用→收工，Solo×Skill 组合规范 v1.0）、`postmortem`（事故简报→时间线与影响重建→根因多视角分析→根因收敛与改进项→复盘报告→收工，Postmortem 实践）、
  `tech_selection`（约束挖掘→对抗辩论→收工）、`knowledge_mining`（专家深挖→整理→收工）、`code_review`（开发→审查打回→收工）、`quality_audit`（多角色独立审→终审→收工）、
  `cross_review`（各自草稿→互看补充→共识汇总→收工，多角色平等协作）、`consensus_building`（各自方案→共识草案→主笔审核三方把关→收工，决策意见汇聚）、
- `design_studio`（设计舱：三视角独立设计→交叉评审→共识定稿——软件/内容/KM 项目设计）
  `wechat_article`（选题定调→素材收集→写稿审核→定稿排版→发布清单→收工，内容生产流程）、`light_dev_flow`（需求精简→架构定调→开发实现→代码审查→发布，中小项目快速迭代——轻量开发流程（需求精简→架构定调→开发实现→代码审查→发布，中小项目快速迭代——全流程 9 轮裁剪版）。
  `iteration_retrospective`（数据收集→分析→洞察→收工，借鉴 retrospective）、`tech_debt_inventory`（扫描→分类→报告→收工，借鉴 tech-debt）、`roundtable_discussion`（轮流发言→互看回应→汇总纪要→收工，3 人以上讨论——零协议改动）、`bid_review`（各自方案→评标择优→中标定稿→
收工，方案选优打回修订）、
  `tiered_review`（产出→技术审查→安全审查→修订定稿→收工，级联把关）、`red_blue_duel`（蓝队立论→红队专职攻击→自由攻防→裁判裁决→收工，不对称对抗）、`red_blue_siege`（蓝队方案→N 红队各自攻击→蓝队防守→裁判汇总裁决→收工，多视角围攻）、`socratic_coaching`（辅导者只问不答→学生思考自悟→辅导总结→收工，引导自悟）。
  用法：`node compose.js --list` 看模板
> **验收轮 / 阶段门禁（借鉴 Game-Studios gate-check）**：分阶段把关不用新机制——单批次内：阶段末加主笔审核轮（软件开发全流程已内置 3 个验收点）。
> 大项目：拆多批次，批末验收不过只重跑该阶段——主笔审核模式即验收轮。 → 复制模板 → 替换 `{角色X}` 占位符 → `node compose.js <改好的.json> [输出目录]`——**"谁先谁后"已按现实团队流程排好，老渣只需填角色和内容**。

## 附录：goal 模式（老渣须知，按需启用）

**goal 模式 = reasonix CLI 的 `/goal` 命令**：角色回合由**平台保活**——回合不因模型输出最终回复而结束，收口靠 `.reasonix-done` 信号文件（非语义判据，换模型不怕）。

**什么时候用**：长期无人值守项目、角色易掉线场景、想根治"回合结束"问题——**通常由用户要求开启，或老渣决策并确认**。

**用与不用的区别**：
- **不开**（默认）：角色普通模式，回合结束靠自觉（第一原则），收工轮角色自觉退场——一切照旧
- **开**：角色窗口 `/goal 持续按公告牌干活` 启动 → 平台保活 → 公告牌警告栏加"禁标 complete/blocked"约束 → 收工轮 touch `.reasonix-done` 收口

**要用时**：警告栏/收工轮要加的内容（逐字稿 + 完整顺序 + evidence 标准 + 常见坑）**全部在 `goal_mode_guide.md`**——打开复制即用，不需要自己设计。

> 平时写普通公告牌**不用管 goal 模式**（警告栏是普通可选约束）；决定开 goal 时再读 `goal_mode_guide.md`。
>
> **工具轮（调查轮/流程体验/AGENTS 自检）**：模板统一在 `通用公告牌/`（调查轮×7 + 流程体验 + 自检），详见「五、工具轮模板」。
